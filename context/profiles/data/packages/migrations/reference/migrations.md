# Database Migration Management

Database migration principles covering Alembic with SQLAlchemy 2.0 async, multi-location sourcing, multi-database support, zero-downtime strategies, and production deployment.

Database migrations track schema changes as versioned, sequential operations that evolve the database alongside application code. Alembic provides migration management for SQLAlchemy 2.0, supporting autogeneration from model changes, async engine integration, and multi-location migration sourcing for monorepo architectures. Disciplined migration practices enable zero-downtime deployments and reliable rollback when schema changes introduce issues.

## Alembic with SQLAlchemy 2.0 Async

Configure Alembic's `env.py` to use `create_async_engine` and execute migrations through `run_sync`. The async runner wraps synchronous migration operations inside the async connection context, maintaining compatibility with `asyncpg` and other async drivers.

Set `target_metadata = Base.metadata` after importing all model modules. Alembic autogenerate compares model metadata against the current database schema to detect additions, removals, and type changes. Import models explicitly in `env.py` rather than relying on side-effect imports -- missing model imports cause autogenerate to miss tables entirely.

### Autogenerate Limitations

Autogenerate detects table additions, column additions and removals, type changes, and nullable changes. It does not detect index renames, data migrations, check constraint changes, or server default modifications. Review every autogenerated migration and add manual operations where autogenerate falls short.

| Detected | Not Detected |
|----------|-------------|
| Table create/drop | Index renames |
| Column add/drop | Data migrations |
| Type changes | Check constraint changes |
| Nullable changes | Server default modifications |
| Foreign key add/drop | Enum value additions (PostgreSQL) |

## Multi-Location Migration Sourcing

Monorepo architectures with multiple packages sharing a database benefit from Alembic's `version_locations` configuration. Each package maintains its own migration directory, and Alembic merges all locations into a single linear history.

Configure `version_locations` as a list of directories, and declare the separator it uses:

```ini
[alembic]
path_separator = ;
version_locations = %(here)s/core/migrations;%(here)s/analytics/migrations;%(here)s/jobs/migrations
```

`path_separator` (Alembic 1.16+, superseding `version_path_separator`) is load-bearing: without it — and without the legacy key — Alembic splits `version_locations` on spaces and commas only, so a semicolon-joined list becomes **one** nonexistent directory and the extra locations are silently ignored (verified with Alembic 1.20.1). `path_separator = os` splits on `os.pathsep`, which is `:` on Linux and macOS. In a pyproject-configured project (`alembic init -t pyproject_async`, or `-t pyproject` for a sync driver), write the locations as a TOML list under `[tool.alembic]` and the separator question disappears.

Each location stores migrations independently. Alembic resolves the combined revision graph across all locations. When migrations from different locations create parallel branches, generate a merge migration (`alembic merge heads -m "merge branches"`) to reunify the history.

### Organization Guidelines

| Guideline | Rationale |
|-----------|-----------|
| One migration directory per domain package | Ownership clarity, independent development |
| Shared `env.py` at the project root | Single configuration point for all locations |
| Explicit model imports per location | Autogenerate only detects imported models |
| Branch labels per location | Prevents accidental cross-location dependencies |

## Multi-Database Support

Data pipelines frequently use PostgreSQL in production and SQLite for local development and testing. Alembic supports both through dialect-aware migrations and conditional operations.

### Dialect-Aware Migrations

Use `context.get_context().dialect.name` inside migration scripts to branch on the target database:

```python
from alembic import op

def upgrade():
    dialect = op.get_context().dialect.name
    if dialect == "postgresql":
        op.execute("CREATE TYPE job_status AS ENUM ('pending', 'queued', 'running')")
    # SQLite has no ENUM type; use CHECK constraint instead
```

### Compatibility Constraints

| Feature | PostgreSQL | SQLite |
|---------|-----------|--------|
| ENUM types | Native | Use CHECK constraints or plain VARCHAR |
| JSONB | Native with indexing | JSON stored as TEXT, no indexing |
| Array columns | Native | Store as JSON text |
| Partial indexes | Supported | Supported (3.8+) |
| Concurrent index creation | `CREATE INDEX CONCURRENTLY` | Not applicable |
| ALTER TABLE | Full support | Limited (no DROP COLUMN before 3.35) |

When a migration uses PostgreSQL-specific features, provide a SQLite alternative or skip the operation for SQLite. Design the core schema using the intersection of features supported by both databases.

## Zero-Downtime Migration Strategies

Production deployments require migrations that apply without taking the application offline. Decompose breaking schema changes into backward-compatible steps spread across multiple deployments.

### Expand-Contract Pattern

Phase 1 (expand): Add the new column or table alongside the existing one. Deploy application code that writes to both old and new locations. Phase 2 (migrate): Backfill data from old to new location. Phase 3 (contract): Remove the old column or table after confirming all reads use the new location.

| Operation | Zero-Downtime Approach |
|-----------|----------------------|
| Add column | Add as nullable with default, backfill, then set NOT NULL |
| Drop column | Stop reading, deploy, then drop in separate migration |
| Rename column | Add new column, copy data, update reads, drop old column |
| Change column type | Add new column, dual-write, backfill, switch reads, drop old |
| Add index | `CREATE INDEX CONCURRENTLY` (PostgreSQL) |

### Lock Management

PostgreSQL migrations acquire locks on modified tables. `ALTER TABLE` takes an `ACCESS EXCLUSIVE` lock that blocks all queries. Minimize lock duration by keeping individual `ALTER TABLE` operations small. Set a lock timeout (`SET lock_timeout = '5s'`) in migration scripts to fail fast rather than blocking application queries during deployment.

## Testing Migrations

Test migrations at two levels: schema correctness against SQLite in-memory for speed, and full compatibility against local PostgreSQL for production fidelity.

| Test Level | Database | Speed | Catches |
|-----------|----------|-------|---------|
| Unit | SQLite in-memory | Seconds | Syntax errors, basic schema issues |
| Integration | Local PostgreSQL | Minutes | Dialect issues, lock problems, data migrations |
| Staging | Production-like PostgreSQL | Minutes | Volume-dependent issues, replication effects |

Use `aiosqlite` with an in-memory database for fast feedback during development. Run `upgrade head`, `downgrade base`, then `upgrade head` again to verify round-trip integrity. Run integration tests against a local PostgreSQL instance matching the production version to validate dialect-specific features, lock behavior, and data migration correctness.

## Production Deployment

Apply database migrations before deploying application code. New code expects the migrated schema. For rollbacks, revert application code first, then downgrade the migration.

| Step | Purpose |
|------|---------|
| Run `alembic check` | Verify no pending autogenerated changes |
| Review migration SQL (`--sql` flag) | Inspect exact DDL before execution |
| Test downgrade path | Confirm rollback works before deploying |
| Back up database | Enable recovery from unexpected issues |
| Apply migration before deploying code | New code expects new schema |
| Monitor lock wait times | Detect blocking caused by migration locks |
| Verify application health after migration | Confirm queries work against updated schema |

## Anti-Patterns

| Anti-Pattern | Problem | Solution |
|--------------|---------|----------|
| Editing applied migrations | Breaks migration history on existing databases | Create new migration to correct issues |
| Multiple logical changes per migration | Complicates rollback and debugging | One logical change per migration file |
| Missing downgrade operations | Cannot roll back schema changes | Include both upgrade and downgrade in every migration |
| Mixing schema and data migrations | Unpredictable lock behavior | Separate DDL migrations from data backfills |
| Skipping local PostgreSQL testing | Dialect issues surface in production | Test against PostgreSQL before deploying |
| Long-running data migrations in DDL transactions | Holds locks for minutes | Run data migrations as separate batch operations |

## Evidence

Alembic's multi-location support ships natively since version 1.0. The expand-contract pattern is documented in PostgreSQL operational guides and adopted by major platforms including GitHub, Shopify, and Stripe for zero-downtime deployments. SQLite in-memory testing provides sub-second feedback for migration chains up to 100 revisions. Production analysis (2024-2026) confirms that separating DDL from data migrations reduces deployment lock time by 80-90%.
